# Удалённое управление

По умолчанию input зоны `dualvpn` равен `REJECT`. Для SSH через туннели задайте
непересекающиеся сети, реально маршрутизируемые VPN-сервером:

```sh
ALLOW_REMOTE_SSH='1'
WG_ADMIN_CIDR='10.10.1.0/24'
AWG_ADMIN_CIDR='10.10.2.0/24'
```

Создаются только два правила TCP/22 с соответствующими source CIDR. SSH в WAN/LTE
не открывается. Отдельные маршруты удерживают симметричный ответ через тот туннель,
из которого пришёл запрос, даже если default route принадлежит другому VPN.

Подключайтесь к VPN-адресу роутера, а не к LAN IP:

```sh
ssh root@10.10.1.2
```

На сервере должны быть корректные AllowedIPs/маршруты к сетям клиентов и разрешён
forwarding между нужными peer. Если Dropbear принудительно привязан к `lan`, он не
слушает VPN-адрес. Не снимайте это ограничение, пока не проверен резервный Ethernet-
доступ.

Выбранный VPN-режим определяет default route, но не выключает второй интерфейс.
Поэтому при активном WG подключение к адресу AWG может продолжать работать — это
нормальный резервный путь управления.

Пример для WG-сервера, где роутер имеет `10.8.1.3/32`, а удалённый компьютер —
`10.8.1.4/32`:

```ini
# peer роутера
AllowedIPs = 10.8.1.3/32

# peer удалённого компьютера
AllowedIPs = 10.8.1.4/32
```

На удалённом компьютере `AllowedIPs` должен включать `10.8.1.3`, а на сервере
должны быть включены IP forwarding и обмен трафиком между peer одного VPN-
интерфейса. Два успешных handshake с сервером не гарантируют peer-to-peer
маршрутизацию.

Если SSH по одному туннелю не работает, смотрите счётчик разрешающего правила во
время попытки:

```sh
nft list ruleset | grep -B3 -A3 '<ADMIN_CIDR>'
```

Нулевой счётчик означает, что пакет не дошёл до firewall роутера; искать причину
нужно в маршрутах клиента, `AllowedIPs` peer на сервере и server-side forwarding.

Рекомендуется SSH-ключ в `/etc/dropbear/authorized_keys`. Отключайте пароль только
после проверки входа ключом и recovery. Для LuCI создайте отдельные HTTPS-правила;
проект намеренно не открывает веб-интерфейс автоматически.
